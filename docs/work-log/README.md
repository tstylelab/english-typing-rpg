# 作業ログ運用方針

このプロジェクトでは、後から作業内容・判断理由・現在の状態を見返せるように、Markdown 形式で作業ログを残す。

## 保存場所

日別ログは次の場所に保存する。

```text
docs/work-log/YYYY-MM-DD.md
```

例:

```text
docs/work-log/2026-06-23.md
```

## Gitでの扱い

日別ログは、個人的な学習状況や家庭内の文脈を含むことがあるため、原則としてローカル保存のみとする。

```text
docs/work-log/*.md
!docs/work-log/README.md
```

上記の設定を `.gitignore` に入れ、日別ログは通常コミット・プッシュしない。

ただし、この `README.md` は作業ログの運用方針としてGit管理に残す。

すでに過去にコミット・プッシュ済みの日別ログがある場合、それを無理に削除する必要はない。今後のログについてローカルのみで運用する。

## 記録する内容

必要に応じて、次の内容を記録する。

- 作業の目的
- 実施した内容や調査した内容
- 変更した主なファイル
- 実装・設計・調整に関する重要な判断ポイント
- ビルド、テスト、手動確認などの確認結果
- 残っている課題や次回やること

## 日別ログのテンプレート

```md
# 作業ログ: YYYY-MM-DD

## 目的

この作業で何を達成したかったのかを書く。

## 実施内容

- 具体的に変更・確認・調査したことを書く。

## 重要なポイント

- 判断理由、注意点、後から思い出したい背景を書く。

## 主なファイル

- `path/to/file`

## 確認結果

- 実行したコマンド、ビルドやテストの結果、手動確認の内容を書く。

## 次回やること

- 残っている作業や確認したいことを書く。
```

## 運用

新しい作業セッションを始めるとき、作業ログが関係する場合はこの方針を確認する。

作業の終わり、またはユーザーから「保存して」「ログに残して」と指示があったタイミングで、その日のログファイルに追記する。

ログは日本語を基本にする。ファイル名、コマンド、コード上の識別子などは、そのまま英語表記やパス表記で残す。

ログは長すぎる必要はない。会話全体を再現するのではなく、目的・重要な判断・変更内容・確認結果が後から分かる程度にまとめる。

コード変更をコミット・プッシュするかどうかと、作業ログを保存するかどうかは分けて考える。ユーザーから明示的に依頼がない限り、日別ログはコミット・プッシュしない。
